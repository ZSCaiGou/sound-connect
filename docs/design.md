# sound-connect 设计方案

## 定位

个人自用的 Windows 桌面工具：把音效和你正在听的音乐送进语音软件，让队友听见。
不对外分发，因此不处理驱动签名、自动更新、安装包体积和跨平台打包。

技术栈：.NET 10 + MAUI Blazor Hybrid（界面用 Blazor，音频走原生 WASAPI，同进程无 IPC）。
早期的 Electron 原型已废弃，代码保留在 `legacy-electron` 标签里。

## 三条硬约束

这三条决定了整个架构，都是实测或平台事实，不是选型偏好：

1. **音频端点必须注册在内核音频栈里。** 用户态没有 API 能凭空造出声卡，所以虚拟线用现成驱动，不自研。自研要写 PortCls/ACX 驱动加签名，本机 Secure Boot 开着、也没装 WDK，这条路彻底排除。
2. **Chromium 的系统回环只能采默认播放设备。** 那意味着整机声音都会进语音，而且 Discord 播放的声音会被绕回去形成回声。排除。
3. **不能改音乐应用的输出设备。** 所以必须做进程级采集（WASAPI 进程回环，要求 Windows 10 2004 以上）。这是唯一能"只抓某个程序"又不碰它的办法。

## 数据通路

```text
QQ音乐/浏览器 ──(进程回环采集 ─ 原生小工具)──┐
                                             ├──→ 扬声器 (Steam Streaming Microphone)
麦克风 + 音效 ──(我们的 app, setSinkId)─────┘              │
                                                          ↓
                                   麦克风 (Steam Streaming Microphone)
                                                          ↓
                                              Discord 输入 ──→ 队友

QQ音乐本身的声音照常进你的耳机：零延迟、零改动
Discord 播放 → 你的耳机：不经过任何被采集的线，所以没有回声
```

关键点：**我们不再采集任何东西**。音乐由原生小工具从进程里旁路抓一份直接送进虚拟线，同时音乐应用照常播它自己的。因为不存在采集，也就不存在回授的来源。整条路只需要一条虚拟线。

## 虚拟线（已实测选型）

本机已有的候选，用 `tools/audio-probe` 实测结果：

| 设备对 | 结果 |
|---|---|
| 扬声器 (Steam Streaming Microphone) → 麦克风 (Steam Streaming Microphone) | **通**。基线 0.0000 / 峰值 0.4656，往返约 20ms，采集端 44100Hz 单声道 |
| 扬声器 (Steam Streaming Speakers) → 麦克风 (Steam Streaming Microphone) | 不通 |
| 扬声器 (网易虚拟音频设备) → 麦克风阵列 (网易虚拟音频设备) | 不通（测试时网易云音乐没运行，结论待定） |

结论：用 `Steam Streaming Microphone` 这个驱动自带的那一对。输出端是我们写混音的地方，输入端是 Discord 的输入设备。

两点要知道：采集端是 44100Hz 单声道，所以整条线的规格就是 48k 重采样到 44.1k 单声道。因为 Discord 语音本来就是单声道，这个限制对最终效果几乎没有影响，只多一次重采样。另外这对驱动是 2017 年的老版本，且实测时 Steam 在运行；**Steam 关掉之后还通不通没有验证**，待测。

**这条线固定加 +30dB，这是踩过的坑。** 从输出端写到输入端，实测增益 31.62x（+30.0dB），用 0.25 和 0.05 两种输入幅度验证过，两次都是 31.62x，是线性增益，不是自动增益控制。所以往线里写任何东西之前必须先衰减 -30dB，否则一律爆表：未补偿时音乐峰值冲到 6.36，超出满刻度 16dB，队友听到的就是削顶的失真声；补偿之后从线的另一端录回来是 0.2019，与送出前的 0.20 一致，正好归一。

这条 +30dB 对音乐、麦克风、音效一视同仁，所以在渲染母线统一乘 0.0316 就行，三者相对比例不变。

## 多进程程序：浏览器

浏览器不自己渲染音频，而是交给子进程。实测 Edge 播放 B 站视频时，音频会话挂在
`msedge.exe --type=utility --utility-sub-type=audio.mojom.AudioService` 这个子进程上，
浏览器主进程（树根）自己反而是"没在发声"的。

两种抓法实测都通：抓那个子进程、抓树根，都能拿到声音。但产品上要抓**树根**——
浏览器会回收音频服务进程，抓子进程的话流会中途断掉。`tools/process-capture` 已经做了自动上溯
（只往上走同名的祖先，所以不会一路跑到 explorer 上）。

实测数据：Edge 播放 B 站视频，树根 PID 44352，采集 48k/2ch/float32，约 375KB/s，峰值约 -13dB；
写进虚拟线后从另一端录回峰值 0.2486，与送出前一致。

## 配置清单

音乐应用零配置，系统默认播放设备也不动。只需要：

1. Discord 输入设备 → 麦克风 (Steam Streaming Microphone)
2. 关掉 Discord 的降噪、回声消除和自动增益（否则持续的音乐会被当背景噪声削掉）
3. 戴耳机（音效的本地监听要走耳机；外放会被麦克风捡到，队友听到两遍）

## 已排除的路线

- **自研虚拟声卡**：内核驱动加签名，见上面第一条。
- **VoiceMeeter / VB-CABLE**：实测本机已有可用的虚拟线，不需要再装。
- **系统回环采集**：见第二条，且有回声。
- **改音乐应用的输出设备**：用户明确不接受。

## 代码结构

```text
SoundConnect/                      MAUI Blazor Hybrid 宿主：窗口、托盘、全局热键、应用生命周期
  Services/AudioEngine.cs          音频通路：设备枚举、进程采集、麦克风、混音、渲染、电平
SoundConnect.Shared/               Blazor 界面（Razor 组件），与宿主同进程，直接调用 C# 服务
  Services/IAudioEngine.cs         界面只认这个接口，实现放在宿主里
src/SoundConnect.Audio/            可复用的底层音频库：进程回环互操作、采集、进程树
tools/audio-probe/                 C# 探针：虚拟线自检（是不是回环）+ 往返延迟实测
tools/process-capture/             C# 进程回环采集器原型：抓指定进程的声音，渲染进虚拟线
```

采集和混音都在宿主进程内，没有独立进程，也就没有控制通道要设计。界面通过
`IAudioEngine` 调进来（RCL 不能引用 Windows 宿主，所以接口放在 Shared、实现放在宿主，
跟模板里 `IFormFactor` 的做法一致）。后续音效池、本地监听输出也挂在这条路上。

## 踩过的三个坑

这三个都是实测撞出来的，改代码时别踩回去：

1. **虚拟线固定 +30dB**：写进去之前统一乘 0.0316，否则一律削顶。
2. **WASAPI 的 COM 对象有公寓亲和性**：在 STA 线程（WinUI 的界面线程）里创建、再拿到采集线程用，`QueryInterface` 直接报 `E_NOINTERFACE`。命令行工具能用只是因为它的主线程是 MTA。所以采集的激活和读取都放在同一个采集线程里做（`ProcessLoopbackCapture` 内部处理）。
3. **NAudio 的 `ToSampleProvider` 不认 `WaveFormatExtensible`**，而设备的混音格式恰好就是它。所以整条链路统一用普通 32 位浮点（字节布局一样，WASAPI 也接受），只从设备格式里取采样率和声道数。
4. **混音块必须整块整块地取**。源缓冲不够一整块时，要在"块边界"上补静音，绝不能在一块中间补：那样源缓冲永远攒不到深度，每个块都会插进一段静音，听感就是持续的卡顿。`BlockAlignedSampleProvider` 负责这件事，它带一个欠载计数，稳定在 0 才说明音频连续。
5. **输出交给设备按自己的节奏来拉**，不要再套一层自己 sleep 的中间缓冲。中间缓冲既加延迟（当时是 150ms），又会为了让缓冲到水位而在中途插静音。现在 `WasapiOut` 直接拉混音图，源缓冲自己预热到几毫秒就稳定了。
6. **源缓冲要限幅并处理时钟漂移**：采集端和输出端是两个独立时钟，跑久了缓冲会缓慢涨上去，涨起来等于白加延迟。超过 150ms 就跳到最新数据。

```text
音频部分的服务划分：

音乐进程 ──(进程回环采集)──┐
                            ├──→ 混音 ──(-30dB 补偿)──→ 虚拟线（队友）
麦克风 ──(WASAPI 采集)─────┘
```

## 验证清单

1. ~~虚拟线是不是回环~~ ✅ 通（Steam Streaming Microphone 那一对，线自身往返约 20ms）
2. ~~进程回环能不能抓到 QQ 音乐~~ ✅ 通（QQ 音乐是单进程，48k/2ch/float32，约 375KB/s，与渲染端格式一致无重采样）
3. ~~采集到的声音写进线之后电平对不对~~ ✅ 通（端到端录回，-30dB 补偿后峰值 0.2019，与送出前一致）
4. ~~浏览器能不能抓~~ ✅ 通（Edge 的音频会话在子进程上，抓树根有效，工具会自动上溯）
5. ~~应用内混音链路通不通~~ ✅ 通（自检模式跑通：音乐 0.045 × 0.7 音量 × 0.0316 补偿 = 总输出 0.001，逐项对得上；从虚拟线录回峰值 0.1302，没削顶）
6. 端到端延迟：麦克风这条路用 Discord 回声测试体感
7. 连续跑二十分钟会不会断流、爆音或漂移（采集端和渲染端是两个时钟）
